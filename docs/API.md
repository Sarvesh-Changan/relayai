# RelayAI — API Contracts

Source of truth for Codex **and** Google AI Studio. Request/response bodies are JSON. Zod schemas live in `lib/validations/*.ts` (HTTP) and `lib/ai/schemas.ts` (AI). TypeScript types are inferred from Zod (`z.infer`).

## 1. Conventions
- Base path `/api`. All routes require a Supabase session except `GET /api/health`.
- Every response carries header `x-request-id` (generated by `withApiHandler`, or accepted from the incoming header).
- Success: `200/201 { "data": <payload> }`
- Error: `{ "error": { "code": "<CODE>", "message": "<human text>", "requestId": "req_…", "details"?: <zod issues> } }`
- IDs are UUIDs; dates `YYYY-MM-DD`; timestamps ISO-8601 UTC.

| Code | HTTP | Meaning |
|---|---|---|
| `UNAUTHENTICATED` | 401 | No/expired session |
| `FORBIDDEN` | 403 | RLS/permission denied |
| `VALIDATION_ERROR` | 400 | Zod failure (`details` = issues) |
| `NOT_FOUND` | 404 | Row missing (`TASK_NOT_FOUND`, `MEETING_NOT_FOUND` map here) |
| `CONFLICT` | 409 | e.g. `ALREADY_COMMITTED_OR_NOT_FOUND` |
| `UNPROCESSABLE` | 422 | Business rule: `INVALID_TRANSITION`, `REASON_REQUIRED`, `OUTCOME_REQUIRED`, `NO_CHANGE` (original code in `details.rule`) |
| `RATE_LIMITED` | 429 | Local soft limit |
| `AI_NOT_CONFIGURED` | 503 | `GEMINI_API_KEY` missing |
| `AI_RATE_LIMITED` | 429 | Provider 429 |
| `AI_TIMEOUT` | 504 | Provider call exceeded `AI_TIMEOUT_MS` |
| `AI_PROVIDER_ERROR` | 502 | Provider 5xx/other |
| `AI_INVALID_RESPONSE` | 502 | Output failed Zod after one repair attempt |
| `DB_ERROR` | 500 | Unexpected database error (details never leaked) |
| `INTERNAL_ERROR` | 500 | Anything else |

### Meetings
| Method & path | Body | Response |
|---|---|---|
| `GET /api/meetings?q=&limit=&cursor=` | — | `Meeting[]` (no raw_notes in list) |
| `POST /api/meetings` | `{ title(1-200), meeting_date(ISO), agenda?, raw_notes?(≤20000), participant_ids: uuid[] }` | `201 Meeting` (extraction_status `none`) |
| `GET /api/meetings/:id` | — | `Meeting` + `participants[]` + `tasks: TaskSummary[]` |

```ts
export const CommitBody = z.object({
```

### Tasks
| Method & path | Body / query | Response |
|---|---|---|
| `GET /api/tasks?status=&owner=&q=&overdue=true&sort=due\|updated\|priority&dir=` | `status` comma-separated; `owner` uuid or `unassigned` | `TaskSummary[]` |
| `POST /api/tasks` | `{ meeting_id?, title, description?, owner_id?, due_date?, priority }` | `201 Task` (manual creation; writes `created` history) |
| `GET /api/tasks/:id` | — | `{ task: Task, origin_meeting: {id,title,meeting_date}\|null, original_owner: Profile\|null, history: HistoryItem[] (asc), links: TaskLink[] }` |
| `PATCH /api/tasks/:id` | `{ title?, description?, priority?, due_date? }` (due date change writes `due_date_changed`) | `Task` |
| `POST /api/tasks/:id/reassign` | `{ new_owner_id: uuid, reason: string(1-500) }` | `Task` |
| `POST /api/tasks/:id/status` | `{ status, reason?, outcome? }` (rules below) | `Task` |
| `POST /api/tasks/:id/carry-forward` | `{ meeting_id: uuid, new_due_date?: IsoDate, reason: string }` | `Task` |
| `PUT /api/tasks/:id/links` | `{ links: [{ target_type:'meeting'\|'document', target_id, reason, relevance?, source:'ai'\|'manual' }] }` (replaces non-system context links) | `TaskLink[]` |

Status rules (enforced by RPC, mirrored in the UI): allowed transitions `open→{in_progress,blocked,completed,cancelled}`, `in_progress→{open,blocked,completed,cancelled}`, `blocked→{open,in_progress,cancelled}`, `completed→{in_progress}`, `cancelled→{open}`; `blocked`/`cancelled`/reopen require `reason`; `completed` requires `outcome`.

```ts
Task = { id, display_id, meeting_id, title, description, owner_id, original_owner_id, due_date, priority, status,

TaskLink = { id, target_type, target_id, target_title, relation, reason, relevance, source }
```

### AI endpoints (all: `export const maxDuration = 60`, soft rate-limited, log `AI_REQUEST_*`)
#### `POST /api/ai/extract`
Request: `{ meeting_id?: uuid, meeting_date: ISO, title: string, raw_notes: string(20..20000), participant_ids: uuid[] }`
Response `data`:
```ts
{
  summary: string,
  decisions: { text: string, rationale: string|null }[],
  action_items: {
    title: string, description: string|null,
    owner_name: string|null,        // what the AI read
    owner_id: string|null,          // server-matched profile, else null
    due_date: IsoDate|null, priority: 'low'|'medium'|'high',
    confidence: number,             // 0..1
    source_quote: string|null,      // ≤ 160 chars from notes
    needs_review: boolean, review_reasons: string[]   // e.g. 'Owner "Sam" not found in team', 'No deadline stated'
  }[],
  risks: { text: string, severity: 'low'|'medium'|'high' }[],
  open_questions: string[],
  meta: { model: string, latencyMs: number }
}
```
Server rules after Zod: owner match = case-insensitive full name → unique first-name among participants → unique first-name among all profiles; else `owner_id=null` + `needs_review`. Relative dates ("Nov 2", "next Friday") are resolved by the model using `meeting_date` supplied in the prompt; any `due_date` earlier than the meeting date is nulled with a review reason. Never invent owners/dates: absent → `null`.

#### `POST /api/ai/link-suggestions`
Request: `{ task_id: uuid }` → Response: `{ suggestions: { target_type:'meeting'|'document', target_id: uuid, target_title: string, relevance: number, reason: string }[], meta }`. Candidates come from DB retrieval; any suggestion whose ref is outside the candidate set is dropped. Nothing is saved until `PUT /api/tasks/:id/links`.

#### `POST /api/ai/handover`
Request:
```ts
{ recipient_id: uuid,
  scope: { type:'meeting', meeting_id: uuid }
       | { type:'task', task_id: uuid }
       | { type:'person', from_user_id: uuid } }
```
Response: `Handover` = `{ id, recipient_id, from_user_id, scope_type, status:'open', created_at, brief: HandoverBrief, meta:{model,latencyMs} }` (persisted before returning).

```ts
HandoverBrief = {
  headline: string,
  situation: string,                                         // what happened, ≤ 600 chars
  decisions: { text: string, meeting_id: string|null }[],
  in_progress: { task_id: string, state_summary: string }[],
  remaining: { task_id: string, what_is_left: string }[],
  blockers: { text: string, task_id: string|null }[],
  deadlines: { task_id: string, due_date: IsoDate, note: string }[],
  risks: string[],
  next_steps: { order: number, action: string, task_id: string|null, reason: string }[],
  references: { type:'meeting'|'document'|'task', id: string, title: string, why: string }[],
  gaps: string[]                                              // what could not be determined from the data
}
```
AI-facing version of the same schema uses `*_ref` strings (`ACT-024`, `M1`, `D2`) instead of UUIDs; `lib/ai/handover.ts` maps refs → UUIDs and drops unknown refs (logging `AI_REF_DROPPED` at WARN).

#### `POST /api/ai/insights`
Request: `{}` → Response:
```ts
{ headline: string,
  insights: { severity:'high'|'medium'|'low', title: string, explanation: string,
              task_ids: string[], recommendation: string }[],   // ≤ 5, each task_id must come from signals
  signals: Signal[],                                            // deterministic, always returned
  meta: { model, latencyMs } | null }                           // null when AI unavailable (signals only, 200)
Signal = { ref:'S1', kind:'overdue'|'blocked'|'unassigned'|'reassigned_multiple'|'due_soon', task_id, display_id, title, detail }
```
Insights degrade gracefully: on AI failure respond `200` with `insights: []`, `meta: null` and an `x-ai-degraded: true` header (error still logged).

## 5. Validation & handler contract
`withApiHandler(opts, fn)` → generates `requestId`, creates `log = logger.child({requestId, route, userId})`, authenticates, parses with provided Zod schemas (`body`, `query`, `params`), runs `fn`, maps `AppError`/`ZodError`/Supabase errors to the envelope, logs `REQUEST_COMPLETED` (status, durationMs) or the failure event, and sets `x-request-id`. Handlers must never return raw Supabase errors.
